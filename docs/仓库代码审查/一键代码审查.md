# 一键代码审查（发给 Agent 即可）

## 你怎么用（人看这几行就够）

1. **建议在实现会话之外新开对话**（或工作流点「提交前正式审查」），避免实现 Agent 自己审自己。
2. 把**本文件**拖进 Agent（需要时再拖 `docs/代码开发规范.md`）。
3. 回「全部默认」或答问卷 → Agent 先做**阶段一代码审查**（可修红线），再做**阶段二需求点检**（只验不补功能）。
4. 看报告 + diff；**不要**自动 commit，由你决定是否提交。

## ========== 以下整段 = Agent 必须遵守的完整指令 ==========

你现在进入 **SUNWODA SEVB 仓库变更审查模式**（含可选需求点检）。读到本文件后立刻按下面流程做，不要先写长篇解释，不要当「规程说明书」讲课。

### A. 启动：先问再审（傻瓜式问答）

**立刻**用中文向用户发出下面这份问卷（可原样发出）。用户已在本轮消息里写明的项不要再问。工作流「提交前正式审查」已写明「全部默认」时 → **不要发问卷**，直接用默认执行。

```text
【代码审查】请确认（直接回序号或「全部默认」）：
1. 基线分支/commit？（默认 develop）
2. 审查范围？
   A. 默认：相对基线未合入的提交 + 未提交改动 + 相关未跟踪文件
   B. 仅未提交（含暂存）
   C. 仅某次提交/区间（请写出 hash 或 develop...HEAD）
   D. 仅某些路径（请列出）
3. 模式？（仅约束阶段一代码审查）
   A. 自动：无写权限只出报告；有写权限则修复 P0/P1（及可确定的 P2）
   B. 强制只报告
   C. 强制审查并修复
4. 报告放到哪个 docs 项目文件夹？
   A. 自动判断（单产线→docs/<项目>/；框架或多项目→docs/仓库代码审查/）
   B. 指定项目代号：________
5. 是否做阶段二「需求点检」？
   A. 默认：做（从进度存档/版本变更/本轮 diff 相关规划自行提炼断言并只验）
   B. 不做（仅阶段一）
6. 还有别的要强调的吗？（没有回「无」）
```

- 用户回「全部默认」「直接审」「开搞」等 → **不再追问**，用全部默认值立即执行（含点检=做）。
- 用户只答了部分 → 其余用默认，立即执行。
- **禁止**在已能开审时仍空转解释；问完（或默认）马上干活。

### B. 阶段一：代码审查（可修复）

1. **只审 diff，禁止全库盲扫。** 在仓库根目录用 git 算出变更文件与 patch：
   - `git status`
   - 相对基线：`git diff --name-status <基线>...HEAD`、`git diff <基线>...HEAD`
   - 未提交：`git diff`、`git diff --cached`，并纳入相关 untracked（`.cs` `.xaml` `.csproj` `docs` 下 md/csv/sql 等）
2. **写法标准**：对照 `docs/代码开发规范.md`（若用户未拖、仓库可读则自行读取）；第二篇红线条款 A–H 逐条对照，问题引用条款编号（如 `[P0][B-01]`）。
3. **方法**：精读 diff；对改动的 public 方法/类按需读调用方与接口；触及下方「加严路径」必须扩上下文并提高风险倾向。
4. **级别只用 P0 / P1 / P2**（无 P3）；命中规范条款的**以条款级别为准**（规范 §11），下列为未覆盖时的参考：
   - **P0**：现场事故/误写设备/卡死崩溃/密钥泄露/臆造点位并用于读写；**长时间运行必然 OOM/进程被杀的确定性泄漏**（如每帧原图进内存且无上限）
   - **P1**：竞态、后台改 UI、严重分层破坏、危险 async、吞异常后继续写设备等；**采集/收图/OCR 路径上只增不减的路径字典、未 Dispose 的 HObject、无裁剪的已处理索引、无 Decode 缩略的大图预览**；**FileSystemWatcher 回调阻塞 / 默认小缓冲 / 溢出只弹窗不补扫导致丢检**；**正式文件直写/半截覆盖（模型·DLL·结果 CSV，对照规范 D-05 / R3）**
   - **P2**：命名/文档收尾/可读性/协作规程缺失等
5. **改代码规则（仅本阶段）**：
   - 无写权限或模式=只报告 → **只写报告，不改业务代码**
   - 有写权限且模式允许 → **直接修确认的 P0/P1**（及可确定的 P2）；吃不准工艺/点位 → 标「待人工确认」**禁止臆造**
   - 禁止擅自 `git commit` / `push` / 改 git config
   - 修了某产线代码 → 按 `docs/Agent协作开发规程.md` 更新该项目进度存档 + 版本变更记录顶部一条
6. 阶段一结论写入最终报告的「阶段一」节；**不要**在本阶段因「需求没做完」去补功能（那是阶段二只标 ❌）。

### D. 检查要点（阶段一按触发项查）

- **规程合规**：点位/IP/阈值是否臆造；进度存档/版本变更是否应收尾；有无无关大重构；明文秘密
- **分层**：View 不直访 PLC；重逻辑在 `Services/Project`；DI 构造注入；VM_`/`View`/`[Module]` 命名一致
- **线程 UI**：禁止后台改 UI；优先 `InvokeAsync`；禁止 UI 线程同步死等造成死锁；高频回调只入队
- **异步资源**：少用 `async void`（事件除外且要 catch）；长循环响应 CTS；禁止 `Thread.Abort`；事件要反订阅；IDisposable/图像/句柄要释放
- **FileSystemWatcher / 目录监控**（变更触及 Watcher、监控路径、Created/Renamed/Error、补扫时必查，对照规范 **D-06 / R2**）：
  - 回调是否只入队？有无 Sleep / WaitFileReady / ImRead / 推理堵在回调上？
  - 是否设置 `InternalBufferSize`（建议 64KB）？`IncludeSubdirectories` 是否与业务一致？
  - `Error` 遇 `InternalBufferOverflowException` 是否重启 Watcher + 全量补扫入队（而非只弹窗）？
  - 导入文件夹枚举是否与监控一样递归（若业务需要子目录）？
- **长时间运行内存**（触及 `Services/Project/**` 收图/管线/视觉、`FileSystemWatcher`、补扫、OCR、预览绑定时必查，对照规范 G-06 / R1）：
  - 去重/缓存集合是否处理后 Remove 或 TTL/裁剪？
  - 已处理 idx 内存表是否仅 Open 时裁、运行期永不裁？
  - Halcon：`out HObject` / `ReadImage` 是否 `finally Dispose`？是否需关 temporary_mem_cache？
  - UI：`BitmapImage` 是否 Decode 缩略、同路径不重复加载、日志/结果表有上限？
  - 聚合字典（Pack/电芯）是否有超时收口？
- **正式文件落盘 / 云端下载**（触及模型·DLL 下载覆盖、检测结果 CSV 追加/合并时必查，对照规范 **D-05 / R3**）：
  - 大文件是否先写 `.downloading`（或等价临时名），校验成功后再覆盖正式路径？失败是否保留旧正式文件？
  - 结果 CSV 是否在 Excel 可能占用时仍直写正式文件？是否采用 `.cache` + 临时合并再替换？
  - 合并/下载失败是否截断或半写正式文件？
- **上位机红线**（触及设备、通信、配置落盘、危险动作、定时器、长循环时必查）：按规范第二篇 A–H 对应类别逐条勾选
- **设备**：写 PLC/MES 失败策略清楚；无依据继续写→P0/P1；日志别刷爆盘
- **卡死**：锁内 IO、紧自旋、无出口循环
- **卫生**：不该进库的 bin/日志/密钥；空 catch；AI 味重复堆砌

### E. 阶段二：需求点检（默认做；只验不补功能）

> 策略详见 `docs/仓库代码审查/审查策略-需求点检与单元测试.md`。问卷选「不做」则跳过本节。

**目的**：回答「声明的需求是否真的实现、关键校验是否可能生效」，**不是**再审一遍代码风格。

1. **识别项目代号**：来自报告目录 / 变更路径 / 用户指定；多项目时按主变更产线，其余标「未点检」。
2. **自行提炼断言**（用户不必手写正反例）：阅读  
   - `docs/<代号>/<代号>进度存档.md`（待办 +「关键需求点检」节；无节则从本轮相关待办提炼）  
   - 最近 `版本变更记录` 顶部若干条  
   - 本轮 diff 触及的规划节 / CSV（按 §0 索引点读，勿通读）  
   产出 **3～8 条**可判真假断言（尽量含正例+反例）。需求含糊写不出断言 → 该条 ⏸ 并写清缺什么信息，**禁止臆造工艺/点位**。
3. **核验**（可超出「仅 diff」扩读相关实现；禁止全库无目的盲扫）：  
   - 代码路径是否存在；条件是否恒真（如 `if (true)`）、分支是否接到出口  
   - 若存在独立 `tests/` 且与断言相关：按需 `dotnet test -m:1`（失败则该条 ❌）  
   - 只能静态看到、无法证明运行时 → 状态最多 🔄 或 ⏸，并写「须实机」；**禁止**仅因 grep 到函数名就勾 ✅  
4. **硬禁止（阶段二）**：  
   - **禁止**为凑点检通过而补写业务功能 / 改校验逻辑  
   - **禁止**把点检 ❌ 改成 ✅ 却无代码证据  
   - 缺功能 → 报告标 ❌，并写「请另开实现会话修复后再审」  
   - 阶段一已允许的规范类修复不受本条限制  
5. **回写进度存档**：若存在或可新建「关键需求点检」节，按本轮断言更新状态与证据摘要（路径/测试名）；**只增改本轮相关行**，禁止整表重写历史。  
6. 点检结果写入同一份审查报告的「阶段二」节（见模板）。
