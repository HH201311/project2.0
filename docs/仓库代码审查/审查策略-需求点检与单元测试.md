# 审查策略：需求点检 + 单元测试

> 版本：2026-10-14　适用：SUNWODA SEVB 全部产线子项目（AIPredictive、CTOL、BoxGluing、CCTB…）  
> 结论：**不再为 AI 产出增加新的审查环节；把力气放在「需求是否真的实现、校验是否真的生效」上。**  
> 样板：`docs/BoxGluing/BoxGluing进度存档.md` →「关键需求点检」节  
> 规程：`docs/Agent协作开发规程.md` §2.5 / §3.7

---

## 1. 立场

现有 [AGENTS.md](../../AGENTS.md) 的收尾要求（进度存档 / 版本变更记录）+ commit 级审查 + **人工实机测试**，已经够用。

- **不引入**外部门禁框架、多智能体审查流水线、额外审查报告制度。
- **不追求**「更严格的审查 prompt」。审查是查「写错了没有」，而我们要查的是「**要求的东西到底做了没有、做了是否生效**」——这是两件事。
- 目的收敛为两条：**功能能正常实现**；**以前犯过的错不再犯**（案例库 + 规范 R1–R3）。

---

## 2. 手段一：每项目「关键需求点检」

**不新建第四份文档。** 写在该项目 `docs/<代号>/<代号>进度存档.md` 内。

### 2.1 推荐写法（与旧待办表并存）

保留原有待办表（`# | 任务 | 状态 | 验收 | 详规索引`）不动日常排期；另设一节 **「关键需求点检」**（样板见 BoxGluing）：

| ID | 需求（一句） | 验收断言（可判真假） | 证据形式 | 怎么证明生效 | 状态 |
|---|---|---|---|---|---|
| R-07 | 只采伺服最大扭矩 | 输出 CSV 列与 `采集块_伺服.csv` 的 230 点一致；气缸列为 0 | 单测 + 实机 CSV | 单测断言点位集合相等；实机跑一轮比对列数 | ✅ |
| R-12 | 机台状态门控 | `AndonRunStatu != 7` 不读扭矩、不写 CSV；`=7` 才读 | 单测（假 PLC 返回码） | 遍历状态码断言分支；日志出现状态变更行 | ✅ |

也可只把**本轮关键行**的「验收」改写成可判真假断言，并在同行或脚注写清证据——不必整表改列。

### 2.2 三条硬规矩

1. **断言必须可判真假。** ✗「版本校验已实现」　✓「`1.2.3` 放行，`1.2.2` 拒绝并返回错误码 X」。
2. **证据强度三级，越低越不可信**：
   - ① 单元测试
   - ② 带可查痕迹的实机测试（日志 / CSV / 截图，**带时间戳**）
   - ③ 静态检查（grep 到代码就勾 ✅）
   **关键断言至少到第②级**；第③级抓不住 `if (true)`。
3. **状态只用** ✅ / 🔄 / ⏸ / ❌；**⏸ 必须写清卡在谁身上**；**禁止把 ⏸ 写成 ✅**。

> 点检时机：每轮收尾勾本轮相关行（与进度存档同一次动作）；发替换包前对关键项做一次确认。

### 2.3 新旧项目兼容（渐进，不强迫）

| 情况 | 做法 |
|------|------|
| **新建项目** | 进度存档带空的「关键需求点检」节（可仅含表头 + 一行「菜单可进」）；**禁止**为点检补造业务码或空单测 |
| **已有进度存档、无点检节** | 继续开发即可；本轮若动到关键逻辑，**只新增/升级本轮相关点检行**，禁止整表重写、禁止「只为对齐格式」开文档轮 |
| **工作流完整性校验** | 仍只认三文档齐全；**不把「有无点检节」当作缺文档** |
| **Agent「已完成」** | 不算证据；须落到测试失败条件或带时间戳的现场痕迹 |

## 3. 手段二：只对关键逻辑写单元测试

工具：**.NET 8 + xUnit**。项目放独立 `tests/` 目录，**不进 `SUNWODA_SEVB.sln`**，按需 `dotnet test -m:1` 运行——避免污染主构建，也绕开本机 MSBuild 多节点静默失败的老坑。

| 该测（纯逻辑，无 UI / 无硬件） | 不该测 |
|---|---|
| 版本 / 授权 / 开关校验 | View、ViewModel 的 UI 行为（Dispatcher） |
| 阈值、判级、分级预警规则 | 真实 PLC / Socket / MES 通信 |
| 状态机迁移（如 `AndonRunStatu` 门控） | Python 互操作、算法模型 |
| 协议字段解析、地址常量拼装 | 图像处理与 OpenCV 流程 |
| 采集块 Loader 选表、CSV 表头映射 | 数据库实连、建表 |

**不追求覆盖率**，只求「点检表里每条关键断言都有一条测试在管」。  
**新建 demo 阶段不建 `tests/`**——有可假输入的纯逻辑后再补。

### 防「测试写了却没管住」：变异测试（可选加强）

用 [Stryker.NET](https://stryker-mutator.io/docs/stryker-net/introduction/) 对**关键校验**做一次变异：把 `==` 改成 `!=`、把 `if` 条件取反，看测试**会不会失败**。

- 测试失败 → 该断言确实被测试管住了。
- 测试仍全绿 → 那条校验等于没验证。

对版本号、门控、阈值这几类，跑一次变异比十份审查报告有说服力。

## 4. 与「一键代码审查」的分工

| 手段 | 回答的问题 | 何时做 |
|------|------------|--------|
| 需求点检 +（可选）单测 | 需求做了没有、校验是否生效 | 功能收尾 / 发替换包 |
| [一键代码审查.md](./一键代码审查.md) | diff 是否踩红线、是否重犯案例坑 | 提交前 / 工作流「正式审查」 |
| 人工实机 | UI、PLC、时序、联调 | 现场或本机联调 |

**禁止**再增加第三道泛化「项目审查」。案例库（本目录 `案例-*.md`）继续沉淀踩坑，供审查触发时对照。
