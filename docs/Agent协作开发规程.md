# Agent 协作开发规程

> **用途**：用人机对话从 0 到 1 上手平台、建新项目、持续开发——不是通读详规。  
> **读者**：新入职开发 / 自己用 Cursor Agent 做产线模块。  
> **样板**：`docs/BoxGluing/`（三文档 + CSV + 代码入口已齐全）。  
> **关联**：平台细节见 [项目架构说明](./项目架构说明.md)、[新增业务模块上手指南](./新增业务模块上手指南.md)。

---

## 0. 核心原则（先记住这 5 条）

1. **问题导向**：带着目标问 AI，对照仓库验证；不要被动通读长文档。  
2. **热层 / 冷层**：新会话默认只拖「进度存档」；规划、点位、历史按索引再开。  
3. **事实只写一处**：点位→CSV；范围与架构→规划；待办→进度存档；历史→版本变更。  
4. **单会话单目标**：一个功能节点一会话；做完可保留；换功能则新开。  
5. **幻觉即止损**：越改越不对 → 回滚到本会话开始前的 git 点 → 新开会话重述需求。

| 文档 | 角色 | 谁维护 | 新会话 |
|------|------|--------|--------|
| `<项目>进度存档.md` | 热层：状态 / 待办 / 代码入口 / §0 索引 | **AI 收尾必更** | **默认只拖这份** |
| `<项目>版本变更记录.md` | 变更历史：背景 / 做法 / 落点 | **AI 收尾追加** | 追溯时再开 |
| `<项目>项目开发规划.md` | 冷层详规：原因、范围、对接、资料 | **人为主，AI 协助**；资料录入后由 AI 从「开发资料」整理更新 | 按索引进节 |
| `开发资料/` | **原始/现场资料投放区**（PLC 表、截图、说明等） | 人投放；工作流「开始录入」后由 AI 读入并整理进规划/CSV | 录入时打开 |
| CSV / SQL / 接口说明 | 已整理的数据真相 | 资料变更时 | 按索引打开 |

## 一、基础理解（平台级，做一次即可）

> 目标：产出两份**可复用上下文**（短、可执行），供后续建项目与开发会话使用。  
> 分支：`develop`。不要一次会话又讲框架又建业务。

### 1.1 可选：生成 `.cursorignore`（由 AI 写文件）

减少 Agent 误读大文件 / 二进制。**不要手抄清单**——把下面 Prompt 交给 Agent，由它扫描仓库后生成仓库根目录的 `.cursorignore`。

**可复制 Prompt：**

```text
请为当前 SUNWODA SEVB 仓库在根目录生成（或更新）.cursorignore。
目标：减少 Cursor / Agent 误读大文件、二进制、构建产物，但不影响日常业务开发检索。

要求：
1. 先快速扫仓库：找出体积大、生成物、原生库、日志、压缩包等路径，再写 ignore 规则
2. 应当忽略：bin/、obj/、.vs/、packages/、*.user、Dlls/ 与各类 *.dll/*.pdb、logs/Log/*.log、备份损坏文件（如 *.bak*）、现场原始大包等
3. 禁止忽略：docs/；业务源码 ViewModels/、Views/、Services/Project/；Core 下 Interfaces/Project、Models/Project；以及 *.cs / *.xaml / *.csproj / 解决方案与本规程相关 md
4. 若根目录已有 .cursorignore，在原有基础上合并去重并说明增删理由
5. 直接写入仓库根目录 .cursorignore；写完后用几行中文说明「忽略了什么、刻意保留了什么」
```

**自检**：打开 `.cursorignore`，确认 `docs/` 与业务 `.cs`/`.xaml` 未被忽略。

### 1.2 理解框架结构

**附件**：`docs/项目架构说明.md`（可再拖 `App.xaml.cs`）。

**可复制 Prompt：**

```text
我是新入职开发，仓库是 SUNWODA SEVB（develop）。请根据附件与解决方案结构：
1. 用表说明各 csproj 职责，以及日常最常改哪些
2. 从 App 启动到业务页面显示的调用链（类名 + 文件路径）
3. 一个业务模块通常涉及哪些目录（VM / View / Service / Core）
要求：只引用仓库里真实存在的路径；搜不到就说没有。输出控制在一页内，我确认后固化为 docs/平台框架摘要.md。
```

**自检**：能否说出「页面 / VM / 项目服务 / Core 接口」各在哪一层？

### 1.3 知道「新增一个任务」要做什么

**附件**：`docs/新增业务模块上手指南.md`。

**可复制 Prompt：**

```text
对照仓库里已有示例（如 BoxGluing 或 LiWeiTest）指出真实路径。不要贴大段模板代码，先给检查清单。
```

**自检**：能否独立说出「三个名字必须对得上」和「菜单靠数据库启用」？

## 二、新项目构建（项目级）

> 顺序：**先可编译的菜单页骨架 → 再建 `docs/<项目>/开发资料/` 并投放现场资料 → 工作流「开始录入」整理进规划/CSV → 再持续开发待办**。  
> 参照：`docs/BoxGluing/`。

### 2.1 向 Agent 说明（可复制）

```text
请阅读 docs/Agent协作开发规程.md，并参照 docs/BoxGluing/。
我要新建项目，代号：{{PROJECT_CODE}}。

请直接做「项目基础结构 demo」（能编译、菜单可进空页），并创建 docs/{{PROJECT_CODE}}/ 下三份文档：
1. {{PROJECT_CODE}}版本变更记录.md — 之后每次改码由 AI 追加
2. {{PROJECT_CODE}}进度存档.md — 待办/已完成/入口/§0 索引；之后由 AI 维护
3. {{PROJECT_CODE}}项目开发规划.md — 原因、需求、对接方、计划、验收、边界、资料索引；我后续手改为主

同时创建空目录 docs/{{PROJECT_CODE}}/开发资料/（现场原始资料投放区，见规程 §2.2）。

三文档结构与写法对照 docs/BoxGluing/（进度存档热层、版本变更倒序、规划冷层）；占位符见本规程附录 A，全部换成真实值。
进度存档须含「关键需求点检」节（对照 BoxGluing 样板：可仅表头 + 一行「菜单可进」）；新建 demo **不要**为点检补业务码，也 **不要**建空 tests/。
代码侧按「新增业务模块上手指南」建 VM/View。
工作流页已确认项目代号：直接落盘改仓库，不要再出方案等确认。
[Module] 第二个参数写左侧菜单显示名（可自拟简短中文或用代号，勿另要「项目中文名」）。
enable SQL：写入 docs/{{PROJECT_CODE}}/enable_*.sql，并按上手指南 / BoxGluing 样板对目标库直接执行（库名以 appsettings.json 为准）；不要只生成文件不执行。
完成后必须：本地编译通过（0 error）；在回复中明确告知「请完整退出 SEVB 应用后重新启动，再在左侧菜单进入新页面」。
```

### 2.2 开发资料目录与录入

**约定路径**：`docs/{{PROJECT_CODE}}/开发资料/`

| 放入这里 | 不要放入这里 |
|----------|----------------|
| 现场 PLC 点位表、设备信息、工艺阈值原始表/截图/说明 | 已整理定稿的 CSV（整理后放在 `docs/{{PROJECT_CODE}}/` 根下，由规划 §0 索引） |
| 对接说明、接口文档、现场照片（可检索的说明类） | 无关压缩包、整包备份、大体积 DLL（DLL 按平台约定目录） |

**工作流（dsh-swd-workflow）**：

1. 选定项目且三文档齐全后，进入「开发资料」步骤（缺三文档则先补文档，不要直接做资料录入）。  
2. 若尚无 `开发资料/`，插件**自动创建**空目录。  
3. 目录内无业务文件时：提示把资料拷入该文件夹；可选 **开始录入**（有文件时）或 **跳过**。  
4. **开始录入**（首次）：把文件清单写入规划「开发资料录入」节，并生成「初次录入」Prompt，由 Agent 阅读资料整理为规划章节与 CSV，更新进度存档 §0；完成后写入录入标识。  
5. **跳过**：写入跳过标识，可进入后续功能步骤；以后可再次录入。  
6. **再次录入 / 更新录入**：枢纽重新打开开发资料后，若此前已 `ingested` 或规划已有「§0 开发资料录入」节，生成 **增量更新** Prompt（先读已有规划/CSV，再对照新资料补差；禁止从零重整理）。按钮为「更新录入」。  
7. **录入标识**：`docs/{{PROJECT_CODE}}/开发资料/.swd-materials-status`（`ingested` / `skipped` / 重新打开后可为 `pending` + `mode=update`）。有 `ingested`/`skipped` 则工作流不再强制停留在本步。

**可复制 Prompt（开始录入 · 首次）：**

```text
【SWD工作流】
当前仓库：{{REPO_ROOT}}
当前项目：{{PROJECT_CODE}}
任务：开发资料初次录入（只整理资料，不改业务 .cs/.xaml）。

1. 阅读 docs/{{PROJECT_CODE}}/开发资料/ 下全部业务文件（跳过 .swd-* 标识文件）。
2. 将已知事实整理进 docs/{{PROJECT_CODE}}/{{PROJECT_CODE}}项目开发规划.md 对应章节；点位/设备/参数落为 CSV（放在 docs/{{PROJECT_CODE}}/ 根下，勿把原始大包再拷一份进根目录）。
3. 更新进度存档 §0 索引链接到新 CSV/规划节；未知项标 ⏸，禁止臆造。
4. 保留开发资料/ 内原始文件不删。
5. 用中文简要汇总：读了哪些文件、写入了规划哪些节、新建了哪些 CSV。
```

**可复制 Prompt（更新录入 · 再次）：**

```text
【SWD工作流】
当前仓库：{{REPO_ROOT}}
当前项目：{{PROJECT_CODE}}
任务：开发资料更新录入（已有整理成果，禁止从零重做）。

1. 先读规划已有章节与 docs/{{PROJECT_CODE}}/ 下已有 CSV，弄清当前结论。
2. 再读开发资料/ 下业务文件，增量：新增补入、变更覆盖、未变跳过。
3. 不要整章重写无关内容；仅更新有变化的 CSV/规划节。
4. 未知项标 ⏸，禁止臆造；保留原始文件；不改业务 .cs/.xaml。
5. 短汇总：哪些新增/变更、改了哪些节与 CSV。
```

### 2.2.1 补齐三文档时（工作流「缺文档」Prompt）

Agent **不得**再从解决方案根目录做「框架结构探查」类待办。平台结构以已有文档为准：

1. `docs/Agent协作开发规程.md`  
2. `docs/项目架构说明.md`（或 `平台框架摘要.md`）  
3. `docs/新增业务模块上手指南.md`  
4. 格式样板：`docs/BoxGluing/` 三文档  
5. 本项目 `docs/<代号>/` 下已有接手指南、改造指南、审查报告等  

仅在文档不足时点读该项目 Views/ViewModels 入口文件；未知点位标 ⏸。

### 2.3 会话默认规则（已落库）

两套加载机制，**内容应对齐**，勿只维护其中一份：

| 工具 | 自动加载的文件 | 说明 |
|------|----------------|------|
| **DeepSeek Harness（DSH）** | 仓库根目录 [`AGENTS.md`](../AGENTS.md) | `dsh-agent-instructions` 默认候选；**不读** `.cursor/rules/*.mdc` |
| **Cursor IDE Agent** | [`.cursor/rules/agent-project-workflow.mdc`](../.cursor/rules/agent-project-workflow.mdc) | Cursor alwaysApply Rule |

核心约束（两份文件均应体现）：

1. **工作流点选优先**：Prompt 已含 `【SWD工作流】` / 项目代号 / 明确任务时，**禁止**再问项目、再出方案等确认；直接执行。  
2. **仅无项目上下文时**才问一次「当前正在开发哪个项目？」。  
3. **写码前置红线（薄约束）**：遵守 `AGENTS.md` §3 短清单与 `docs/代码开发规范.md` 第二篇最高频 P0；完整条文不塞进 Agent 指令；**不要**加载 GTVR / 自检回执流水线。  
4. **每次代码变更收尾**：轻量自审（尽量带条款号如 `[P0][B-01]`）→ 更新进度存档（含本轮相关**需求点检**）→ 版本变更顶部追加；规格变了再改规划（勿问「要不要更新文档」）。  
5. **思考与过程一律中文**：分析、计划、推理、工具说明、中间步骤与对用户回复均用中文（代码标识符、路径、协议字段、原文引用除外）。  
6. 正式提交前审查：拖 `docs/仓库代码审查/一键代码审查.md`，或工作流枢纽「提交前正式审查」（全部默认；发现问题自动修复并写报告；**不自动 git commit**，由人检查后手动提交）。不必每轮都做。  
7. **需求是否真完成**：靠进度存档「关键需求点检」+（可选）单测/实机证据，**不**另加「项目审查」环节。详见 [审查策略-需求点检与单元测试](./仓库代码审查/审查策略-需求点检与单元测试.md)。

人侧配合：优先走 `/swd-workflow` 点选再进聊天；或第一句写清项目代号 / 拖进度存档。

### 2.5 需求点检与单元测试（完成度，非审查）

> 真相源：[仓库代码审查/审查策略-需求点检与单元测试.md](./仓库代码审查/审查策略-需求点检与单元测试.md)；样板节：`docs/BoxGluing/BoxGluing进度存档.md`「关键需求点检」。

| 规则 | 说明 |
|------|------|
| 不新建文档 | 点检写在进度存档内；待办表可继续用旧四列 |
| 断言可判真假 | 含正例 + 反例；禁止「已实现」这类空话 |

| 单测 | 仅纯逻辑；独立 `tests/`、不进主 sln；新建 demo 不建空测试 |
| 与一键审查 | 点检验「做了没」；一键审查验「diff 踩红线没」——分工，不叠第三道 |

## 三、持续开发

### 3.1 新会话必须先指定项目

```text
当前项目：{{PROJECT_CODE}}。请先读 docs/{{PROJECT_CODE}}/{{PROJECT_CODE}}进度存档.md，
再按待办 #N 做：……（一句话目标 + 验收标准）
```

### 3.2 节点结束 → 本地 git 存档

每个开发节点（可演示的一小步）结束后：

- 更新进度存档 + 版本变更（Agent 收尾）  
- **本地 commit**（或你明确要求再 push）；方便回滚与回溯  
- Agent **不得擅自** `git push` / 改 git config / 强推；**仅在你明确说「提交」时**再 commit

### 3.3 会话边界

| 情况 | 做法 |
|------|------|
| 当前模块还在改、上下文仍有效 | 保留同一会话 |
| 换新功能 / 新待办大项 | **新开**会话，重新指定项目与目标 |
| AI 幻觉、越改越乱 | **回滚本会话开始前的 git 点**，新开会话，重述需求（可附「上次错在哪」） |

### 3.4 需求怎么说

1. 先完整描述目标与验收；不清楚就多轮让 AI **只出方案/数据流**，你核对后再让 Agent 改码。  
2. 抽象概念用**举例**或**简图**；有读图能力时，界面异常可截图并圈出问题点。  
3. 待确认项（进度存档里标 ⏸ 的）问人，不要让 AI 猜 PLC/工艺真相。

### 3.5 推荐单目标 Prompt

```text
当前项目：{{PROJECT_CODE}}。请只做进度存档待办 #N：{{标题}}。
验收断言（可判真假）：{{正例 + 反例}}。
证据形式：单测 / 实机日志或 CSV（带时间戳）。
先读进度存档与 §0 指向的规划节/CSV，给出：改哪些文件、是否动接口、风险。
不要直接贴大段代码；我确认方案后再分步实现。
收尾：更新进度存档（待办 + 本轮关键需求点检行）与版本变更记录；有纯逻辑则补 tests/ 对应用例。
```

### 3.6 需要注意的点：

| 规则 | 说明 |
|------|------|
| 事实源优先级 | PLC/IP/阈值以 CSV 为准；待办以进度存档为准；规划不重复抄点位 |
| 单会话单目标 | 禁止「把整个 P0 一次做完」 |
| 先方案后改码 | 工业逻辑先对齐再写，先使用ask模式多轮对话确认颗粒度是否对其 |
| 资料进仓 | 原始资料放 `docs/<项目>/开发资料/`；整理后的 CSV/说明放 `docs/<项目>/` 根下并由规划/进度存档索引；大体积 DLL 按约定路径 |
| 完成度 | 关键需求看点检证据，不另开「项目审查」；旧进度存档无点检节时本轮相关行再补 |

### 3.7 旧进度存档无点检节时

1. **不要**一次性改写全部历史待办。  
2. 本轮若实现/修改关键逻辑：在进度存档增加「关键需求点检」节（或补行），写入本轮断言与证据。  
3. 禁止单独开一轮「只对齐文档格式、不改业务」。
