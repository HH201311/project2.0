#### 2.4.2 三个卡点（当前无法直接采集现场这批点位）

| # | 卡点 | 证据 / 说明 | 处置 |
|---|------|-------------|------|
| 1 | **采集模型是「连续地址块 + 字节偏移」，现场是「符号寻址」** | 平台链路：`plc_rw_config`（`area_name`+`start_address`+`length`）→ `ReadAddressRangeAsync` 读整段字节 → `ConvertValue(bytes, type, index*addressWordLength, bitIndex)`。`PLCRWConfig.AddressType` 注释即 `0=标签地址 / 1=地址块`。本仓 BoxGluing 用的就是连续地址（`D1600/D1601…`）。而现场：伺服 `ar_` 148 个 + `st…` 结构体 772 个；气缸 `ar_` 698 个 + `st…` 976 个，均非连续偏移模型。（平台 `Read(address, length)` 本身可传符号字符串，但**上层轮询是按块取字节再切偏移**，不适合符号逐点语义） | 需专为符号点位写采集实现（按变量列表批量读），**不能靠配置现有的 `plc_rw_config` 直接套用** |
| 2 | **类型映射缺 `REAL` 别名** | `ConvertValue()` 只认 `FLOAT/DOUBLE/INT/BOOL…`，`REAL` 落到 `_ => null` **静默返回空值**；而伺服 920 点全为 `REAL`。`PLCDevice.WriteAsync` 侧已有 `"FLOAT" => "SINGLE"` 别名，说明读取侧只是漏了 | 小改动：读取侧补 `REAL`/`LREAL` 别名（本轮未改代码） |
| 3 | **结构体成员点号访问** | 数组下标有 HSL 示例；成员路径 `stEM*.….rActPos` **现场已可读**。整根 `ReadStruct`/按字节块读 **不可用**；加速用 **multi-tag Read**（见 CIP 汇报） | ✅ 2026-09-11 全量实测；主程序已 multi-batch |

#### 2.4.3 待现场实测项（⏸ 禁止臆造）

| # | 待测项 | 为什么必须实测 |
|---|--------|----------------|
| 1 | **端口 8500** | EtherNet/IP 显式报文标准端口是 **TCP 44818**；公开来源中**查不到 8500** 用于欧姆龙 CIP 的依据。现场需用 `netstat`/Wireshark 核实真实监听端口 | 
| 2 | 现场变量是否已**公开为网络变量** | CIP 只能访问已注册的全局/网络变量；未公开的驱动对象（如伺服轴参数）读不到 |
| 3 | `st…` 结构体成员能否按点号直读 | HSL 无官方示例，可能只支持整体读 |
| 4 | 单个变量/结构体的**字节长度** | 平台 `Device.Read(address, length)` 的 `length` 是**字节数**（`ReadAddressRangeAsync` 用 `rwConfig.Length`），符号读必须给准长度 |

### 3.5 采集存储与跨部门取数方案（2026-09-10 调研，⏸ 待定位确认后定稿）

> **背景**：原设想用 CSV 文档存储采集数据；但点位达 2594 个（§C.0），按 1 s 采集即 **2.24 亿点/天**，CSV 方案在 TB 级不可用。以下为调研结论，**选型未拍板**。  
> **过渡落地（2026-09-10；2026-09-22 更新）**：在时序库选型前，先用 `AIPredictiveCsvStorage` 落盘——根目录 `D:\AIPredictiveData`、按天 `yyyy-MM-dd`、单文件 **100MB** 滚动、保留 **30 天**自动删目录；宽表一行一轮。**2026-09-22**：CIP 基周期 **500ms**（现场确认标准间隔），同一快照按轮次分写三套文件 `AIPredictive_{500ms|1s|5s}_yyyyMMdd_nnn.csv`（每 1/2/10 轮），供大数据组按粒度取数。仍属过渡，长期仍以 §3.5.2 时序库为目标。

#### 3.5.1 为什么 CSV 不能做主存储

| 问题 | 说明 |
|------|------|
| 无索引 | 按时间窗 + 点位聚合查询在 TB 级全量扫描，分钟级等待 |
| 并发冲突 | 多部门同时读写同一文件会锁冲突；单文件 GB 级后打开即卡 |
| 运维困难 | 按时间清理/归档需重写整个文件；无原生分区裁剪与压缩 |
| 无类型 | `BOOL` 落成字符串、`REAL` 丢精度；无单位与 schema 版本管理 |

> 本仓既有 CSV 实践（CCTB / JROH / JRCW / PTO / JRRY 等 `*CsvHelper.WriteCSV`）均为**批次结果落盘**（每只电芯 / 每批次一行），**不是**连续高频时序采集——CSV 在本项目应**降格为导出/交换格式**。

#### 3.5.2 时序库选型对比（⏸ 待定）

| 方案 | 优势 | 代价 | 适配 |
|------|------|------|------|
| **TimescaleDB**（PostgreSQL 扩展） | 标准 PG 生态（JDBC/ODBC/psycopg 通吃）；SQL + 窗口函数；`create_hypertable` 自动时间分区；`add_retention_policy` 自动清理；`continuous_aggregate` 内置降采样；**Excel 可经 PG ODBC + Power Query 直连** | 需独立 PG 实例（平台现用 MySQL，多一套运维） | ⭐ 若以「分析部门自助取数」为重 |
| **InfluxDB v2/v3** | 采集生态最强（Telegraf）；内置任务引擎与 UI；写吞吐高 | Flux 语言学习成本（v3 转 SQL）；开源版集群/保留能力受限 | ⭐ 若以「设备接入 + 实时看板」为重 |
| **QuestDB** | 写入快；SQL + PG wire；原生 `EXPORT PARQUET` | 生态较小 | 备选 |
| 现有 MySQL 加分区 | 零新增基础设施 | 无原生压缩/降采样，高频写入压力大，保留策略与降采样需自建 | 仅过渡 |
| 纯 CSV / Parquet 文件 | 零依赖 | §3.5.1 全部问题 | 仅冷归档 |

> **推荐**：采集与存储解耦——采集服务只负责「取数 + 批量写库」；降采样、保留策略、导出交给时序库自身能力，**不自己写定时 CSV 任务**。

#### 3.5.3 跨部门取数：三通道分工（回答「导出给其它部门方便吗」）

| 通道 | 适用 | 做法 | 建议对象 |
|------|------|------|----------|
| ① **只读 SQL 直连** | 需反复探索、按需查询 | 开只读账号（**建议只读副本**，避免拖慢采集库）；对方用 psycopg/JDBC；Excel 走 PG ODBC + Power Query | 数据分析 / 算法团队 |
| ② **Parquet 批量导出**（主通道） | 拿全量做建模/训练 | 按小时/天分区导出（Hive 分区 + Snappy/Zstd）；比 CSV 小 5~10 倍且保留类型 | 数据分析 / 算法团队 |
| ③ **CSV 导出** | 单次小范围交付、人工查看 | **先按时间窗 + 点位子集做聚合/降采样再导**，必带表头与单位 | 工艺工程师 / 跨部门临时需求 |

**明确不做**：**不要把时序库的数据目录/文件直接拷贝给对方**（与版本强耦合、含 WAL 与权限状态，对方无法启动或会损坏）。对方若要自建，交付「建库脚本 + Parquet 批量导入脚本」即可。

#### 3.5.4 建议的分层存储结构（待定位确认后细化）

```
PLC 采集 → 时序库
   ├─ 原始层：保留 30~90 天（自动 retention）
   ├─ 降采样层：1 min / 1 h 物化视图，长期保留 ← 分析与建模主要用这层
   └─ 导出层：Parquet（主） / CSV（辅） / 只读 SQL 账号（直连）
```

#### C.0 采集频率与数据量（2026-09-10 分析，含 ⏸ 待实测项）

> **2026-09-29 程序当前**：界面选厂家（**先导 / 赢合互斥**）；CIP 周期 **500ms**；端口 **固定 44818**；每轮先读对应 Andon 标签（INT16），**状态=7 采扭矩**；由运行切入异常后 **宽限 3s 仍采**；厂家/IP 取本机 `plc_endpoint.json`。CSV **仅 500ms**。若单轮 CIP >500ms，实际周期以耗时为准。下列 2594 点测算仍是全量盘点口径，对应备份目录。

**数据量测算**（全点位同一周期的推算，非现场实测）

| 采样周期 | 点/秒 | 点/天 | CSV 年增量(≈40 B/点) | 时序库压缩后年增量(≈3 B/点) |
|----------|-------|-------|----------------------|------------------------------|
| 10 ms | 259,400 | ≈ 22.4 亿 | ≈ 305 TB | ≈ 22.9 TB |
| 100 ms | 25,940 | ≈ 2.24 亿 | ≈ 30 TB | ≈ 2.3 TB |
| 1 s | 2,594 | ≈ 2.24 亿¹ | ≈ 3.0 TB | ≈ 229 GB |
| 60 s | 43 | ≈ 374 万 | ≈ 51 GB | ≈ 3.8 GB |

> ¹ 同列相邻行换算口径不同（点数×周期），仅作量级参考。

**业界参考区间**（行业经验区间，非现场标准，⏸ 需与工艺确认）

| 信号类别 | 建议采集方式 | 常见区间 |
|----------|--------------|----------|
| 设备状态 / 到位 / 夹紧（BOOL） | **变化沿触发**最优，轮询会浪费绝大多数存储 | 50~200 ms 轮询（但按沿记录） |
| 过程量（压力 / 温度 / 流量） | 周期轮询 | 100 ms ~ 1 s |
| 动作时间 / 节拍（`rFw_CT`、`rBw_CT`） | **按动作事件抓一次**（按周期采无工艺意义） | 每动作一次 |
| 运动量（`rActPos`/`rActVel`/`rMaxTrq`） | 需瞬态诊断才高频；否则降档 | 10~50 ms（诊断）/ 100~200 ms（过程） |
| 报警 / 故障 | 事件触发 | 事件驱动，不做周期采集 |

**⚠️ CIP 请求速率（2026-09-11 现场实测已更新）**

- 符号点位**不能**整根结构体连读（`ReadStruct` / 按字节块读根标签均失败，见 [现场结论简报-20260911.md](./现场结论简报-20260911.md)）。
- **可行**：`ArrayBatch` 整段连读 + `StructMembers` **多标签批量 Read（方案 E，batch=20）**。
- **全量实测**（2594 逻辑点，产线 `10.147.72.10:44818`）：约 **0.47 s/轮**（min≈0.44 / max≈0.56），相对旧逐成员约 **2 s/轮** 提速约 **4×**。  
- **2026-09-22 扭矩子集**：程序周期 **500ms**（现场标准）；CSV 分写 500ms/1s/5s（见 `AIPredictiveCsvStorage`）。  
- **2026-09-23 机台状态门控**：标签 `AndonRunStatu`（CIP `ReadInt16`）；`7=运行 / 18=停机 / 19=待机 / 9=故障`。  
- **2026-09-24**：异常宽限 **3s**；PLC IP 本机 JSON 可配；CSV **仅 500ms**（去掉 1s/5s）。  
- **2026-09-17 曾用 250ms 四粒度**：数据量偏大，已回调。  
- **2026-09-14 曾试 50ms**：数据量过大已回调。  
- 已知例外：`ar_bIOT2FromPLC2` 现场 Error 5（路径不存在），需工艺/电工核对符号，不否定读法。  
- **若确需稳定 10~50 ms 且点位再扩大**：显式报文可能不够，业内做法是 EtherNet/IP **Class 1 隐式报文**。

**分层采集建议（P0 决策，先做点位筛选）**

| 层 | 对象 | 采集方式 | 预估量级 |
|----|------|----------|----------|
| L1 事件层 | 气缸 BOOL（到位/夹紧/松开，1128 个） | 变化沿 + 动作事件落库 | 与节拍同阶，远小于周期采集 |
| L2 过程层 | 动作时间（546 个 REAL）、工艺过程量 | 动作完成时抓一次 / 1 s | GB/天 级 |
| L3 高频层 | 伺服 `rActPos`/`rActVel`/`rMaxTrq`，**仅关键轴** | 100~200 ms（诊断则 10~50 ms） | 视保留轴数而定 |
| L0 不采集 | 无预测价值点位 | 不采 | —— |

> **收益比选型更大**：把 2594 点按「预测必需 / 仅诊断 / 暂不需要」分档 + 分层采样，年数据量可从 TB 级降到百 GB 级。**这一刀先切，再谈数据库。**
